# domain-engineering-hardware

**When to use:** role-requirements or candidate-assessment is running on a hardware engineering role, and the agent needs field knowledge to set must-haves or to judge evidence.

**When not to use:** Software-only roles; running an assessment without the core skill.

## Purpose

Keep field knowledge out of the role-neutral core skills. This skill adds what a generalist recruiter would miss in hardware: which experience transfers, what real bench ownership looks like, and how hardware resumes inflate. Assistive only, like the core skills it supports.

## Inputs

- The role or candidate material the core skill is already using.

## Outputs

- Additions to the core skill's output: must-haves, transfer notes and education bar (for role-requirements); ownership cues, inflation flags and transfer judgments (for candidate-assessment).

## When defining the role

- **Domain transfer.** Physics transfers within a device family more than across families. Any MEMS part with a moving structure (accelerometer, gyroscope, pressure diaphragm) transfers to another; optical or thermal sensing transfers less. Precision motion work (stages, actuators) often transfers to inertial sensing, because both deal with displacement noise and vibration.
- **Ownership depth.** Name the level per outcome: owner (wrote the test plan, built or ran the setup, analyzed the data, wrote the report), coordinator (compiled results, managed a test house or vendor), simulation-only. Most bench roles need owner level on the core measurement.
- **Skills.** Separate doing from vocabulary. Instrument automation and analysis scripting are skills; knowing a method's name (for example, a noise-analysis term) is not. Equipment by name (rate tables, thermal chambers, probe stations) is resume-observable; running it alone is screen-only.
- **Background.** Device makers and component suppliers work at consumer volume and pace; aerospace and navigation-grade work is slower and deeper. Weight this below direct evidence.
- **Education.** A Master's with real bench time is usually enough for test and characterization. Research-heavy roles may justify a PhD; name the 3-5 research groups that feed the niche in the real profile.
- **Eligibility.** Defense-adjacent work can carry export-control or clearance rules; capture them as eligibility, not as a tier.
- **Environment.** Bench roles need high on-site time. Confirm lab access and on-site days early.

## When reading a candidate

- **Ownership cues:** they name the part, the setup, the instruments, what went wrong and what they changed. Field applications, program, technical lead and "supported customers" titles default to Unverified.
- **Inflation signals:** simulation or modeling presented as measurement; "characterized" when a test house produced the data; yield or performance gains with no baseline; software titles reworded as hardware; tool lists that echo the job description.
- **Trajectory:** a drift toward program or product management means less recent bench time. Read the last two years closely.
- **Transfer judgments:** say which adjacent part family or method the candidate's evidence comes from, and whether that transfers under the rules above.

## Procedure

1. Confirm the role is hands-on hardware work. If not, stop.
2. In role-requirements, apply "When defining the role" to the matching axes.
3. In candidate-assessment, apply "When reading a candidate" in the evidence, inflation, ownership and transfer steps.
4. Keep all output inside the core skill's structure. Do not add axes.

## Worked synthetic example

**Role (synthetic):** sensor characterization engineer at Northwind Devices (fictional wearables maker). Applied to role-requirements: domain must-have is hands-on MEMS parts with a moving structure (accelerometer, gyroscope, pressure diaphragm), any type (transfer rule); ownership depth is Critical at owner level for test plan, data and report (screen); a noise-method name is not required; the education bar is a Master's with bench work.

**Candidate (synthetic):** Sam Okafor, Principal Field Applications Engineer at Brightmoor Sensors (fictional supplier). Applied to candidate-assessment: domain is Strong, not Ideal, because the consumer IMU work is claimed on the profile only; hands-on characterization is Unverified, because a field title defaults there; internal design guides on board layout are claimed and rare; a screen should confirm them. Trajectory: customer-facing for years, so recent bench time is in doubt. Verdict from the core skill: screen first.

## Failure modes / edge cases

- Treating method vocabulary as hands-on skill.
- Reading "characterized" as owner-level work without asking who ran the bench.
- Missing transfer from a nearby part family and filtering out strong candidates.
- Adding new axes instead of feeding the core skill's axes.

## Forever don'ts

- Never run as a standalone verdict; the core skill decides.
- Never hire, reject or contact a candidate.
- No real candidate, client or research-group names in shared examples.
- No production scoring internals.
